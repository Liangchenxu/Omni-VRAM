## 一、做了什么（What Changed）

### 1. 向量化融合算子（C++ / CUDA）
- `WDDM-Bypass/csrc/graph_engine.cu`
  - `kernel_fused_affine_relu_f32`：一次内核完成 `out = max(0, a * scale + b)`，
    三个指针 16 字节对齐时走 128-bit `float4`（`LDG.E.128` / `STG.E.128`），
    不齐时回落标量路径，尾部 1~3 个元素单独处理。

    按名字解析三个静态缓冲、校验 `count * 4 <= bytes`；捕获中 `stream_token=0`
    表示"正在录制的那条流"。
  - `stats()["fused_launches"]` 计数器。

### 2. 外部 PyTorch CUDA Stream 非拥有式捕获
- `begin_capture(graph_id, shape_key, hot_update, stream_ptr)` 新增 `stream_ptr`：
  非 0 时用 `cudaStreamCaptureModeRelaxed` 录制调用方（PyTorch）的流，
  内部流仍用 `ThreadLocal`，`stream_ptr=0` 的行为与 v2.8.0 逐字节一致。
- `resolve_stream()` + `active_capture_stream_` + `capture_uses_external_stream_`；
  `end_capture()` 关闭 `active_capture_stream_`；析构只销毁引擎自己的流。

### 3. 真实模型接管（Python）
- `wddm_bypass/integration.py`
  - `TorchGraphModule`：包装任意 `nn.Module`，三段式 Warm-up → Capture once → Replay，
    按输入形状维护静态张量场，`stats()` 汇报 `Warmups / Captures / Replays / EagerFallbacks`。
  - `DecodeBuffers.fused_affine_relu()`：融合算子的缓冲区视图。
  - `slot_keys()`：暴露每个槽位实际使用的路由键。

## 二、遇到了什么问题与踩坑剖析（Problems & Root Causes）

### 坑 1：4 MiB 只有 1.10x —— 不是提交延迟，是 HBM 带宽墙
v2.8.0 的收益全部来自"少提交几次"。数据量到 4 MiB（1,048,576 float32）时，
提交开销被数据量摊薄，瓶颈换成显存带宽：

```text
未融合 scale -> add -> relu：
  Kernel1  1R(a) + 1W(tmp1)            = 8  B/elem
  Kernel2  2R(tmp1,b) + 1W(tmp2)       = 12 B/elem
  Kernel3  1R(tmp2) + 1W(out)          = 8  B/elem
  合计 28 B/elem  ->  4 MiB 数据 = 28 MiB 流量/次
  Arithmetic_Intensity = 3 FLOP / 28 B = 0.107 FLOP/Byte（严重带宽受限）

融合后（寄存器内完成乘加与截断）：
  1R(a) + 1R(b) + 1W(out) = 12 B/elem  ->  12 MiB 流量/次
  Bandwidth_Reduction_Ratio = 28 / 12 = 2.33x
  Arithmetic_Intensity = 3 FLOP / 12 B = 0.250 FLOP/Byte
```

**根因**：三个 kernel 把中间结果落回显存；不融合就一定要多搬 2.33 倍的数据。

### 坑 2：度量方式本身是错的（读到 0.00005 ms）
第一版基准用 CUDA event 计时，结果每次迭代只有几十纳秒——因为
`cudaEventRecord` 记在默认流上，而工作提交在另一条流上，两者没有排序关系，
量到的只是提交动作本身。**教训**：跨流计时的唯一可靠做法是
`torch.cuda.synchronize()` + 墙钟，或把 event 记在被测的那条流上。

### 坑 3：`BucketPolicy` 把槽位编号并进同一个桶
`TorchGraphModule` 第一版用 `ShapeKey(1, 1, 320 + n)` 当槽位键。结果两个不同输入形状
只产生 1 个图（`Captures == 2` 但 `engine.graphs() == [0]`）。根因是
`wddm_bypass/bucketing.py` 的 `BucketPolicy()` 三个 step 默认 0，
`_round()` 走 `power_of_two_at_least()`：320 与 321 都归到 512，落进同一个桶、
共用一个 graph id。

### 坑 4：预热门槛不是"仪式"，是捕获成功的前提
直接捕获 `nn.Linear` 会失败：cuBLAS 首次调用要建 workspace、
torch caching allocator 要为中间张量建块，**捕获期分配**正是
`cudaErrorStreamCaptureUnsupported` / 捕获失败的经典来源。

### 坑 5：外部流必须用 `Relaxed` 模式
严格模式（`Global` / `ThreadLocal`）下，aten / cuBLAS 在录制期查询流或分配器状态
会被判为非法操作。用 `cudaStreamCaptureModeRelaxed` 才能把真实 kernel 录进图。

### 坑 6：`import vram_core` 在裸 `python.exe` 下弹模态错误框
Windows 加载器在缺少依赖时弹**模态**对话框，进程直接卡住等人点确定；
Python 3.8+ 又用受限搜索标志，`PATH` 对扩展依赖不再生效。

## 三、如何解决的（How It Was Solved）

1. **算子融合 + 128-bit 向量化**：把三次读写合成一次，
   `fmaf` 做乘加、`fmaxf` 做 ReLU 截断，中间结果只活在寄存器；
   对齐判定 `(out | a | b) & 0xF == 0`，不齐回落标量（数值完全一致）。
   实测 12 B/elem 把 4 MiB 的加速比从 1.10x 拉到 **1.78x**。
2. **正确计时**：改为"每轮 40 次迭代 × 5 轮取中位数，每轮前后 `cuda.synchronize()`"，
   并同时测三条路径（eager 三发射 / 三 kernel 图 / 融合图），用后两者之差证明
   收益来自流量而不是提交次数。
3. **槽位键放进 `dtype`**：`ShapeKey(1, 1, 1, "slot-320")`。`BucketPolicy.bucket()`
   只对三个整数维度取整，`dtype` 原样带过，因此每个槽位拿到独立的 graph id。
4. **三段式接管**：先在私有流上 eager 预热 `warmup_steps` 次（把 cuBLAS workspace、
   allocator 块、launch 配置这些一次性开销挪出捕获区），再 `begin_capture(stream_ptr=...)`
   录制，之后每次 `cudaGraphLaunch` 一次跑完"拷入 + N kernel + 拷出"。
5. **Relaxed 模式 + 非拥有语义**：引擎只借用外部流，`end_capture` 关闭录制时用的那条流，
   析构只销毁自己 `cudaStreamCreateWithFlags` 出来的内部流。
6. **DLL 自愈**：`SetErrorMode(0x8003)` 让缺依赖变成可捕获异常；
   `os.add_dll_directory` 注册 Conda / CUDA 目录（`load_backend()` 与 `vram_core` 导入时各调一次，幂等）。
